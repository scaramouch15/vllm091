# 独立候选选择 CPU 微基准

本实验不导入 vLLM，也不接入 Scheduler。A 为一次排序后 pop，B 为每次线性查找最小值后 pop，C 为一次 heapify 后 heappop；统一按 `(score, original_position)` 选最小值。score 是预先生成的有限非负数；P90 可作为分数来源的例子，但不是最终调度公式。不同分数相等时，以原窗口位置保证稳定次序。

N 是整个模拟 waiting 的长度，K 是连续前缀长度，A 是检查次数（包括可能失败的那一次），M 是成功准入次数，A 和 M 不等同，也不能直接等同 `max-num-seqs`。连续前缀仅是隔离数据结构成本的假设，不是生产窗口或公平性方案。

两种计时都从同样的未排序 K 条目开始；三种方法创建各自的数据结构，排序及 heapify 均计入。纯选择计入数据结构构建、A 次选择及返回列表。完整窗口计入从 deque 提取 K 个引用、构造条目、结构构建、A 次尝试与成功记录、按原顺序恢复未成功的前缀；尾部保持原状，未对全队列 remove 或在计时内复制整条队列。各次独立输入 deque 在计时外构造，故报告的完整窗口耗时不包括准备整个 N 长队列的成本。每次都有相同预生成分数、相同模拟停止条件。基准固定每次 A 次成功（M=A），容量为 A；测试另行覆盖容量停止和首次/中途模拟失败立即停止。这个失败控制流不代表真实 KV allocator。

调用方在计时前调用 `validate_scores`，拒绝非有限数、负数、布尔或非数字。内部选择函数以此为前提，并要求 `0 <= A <= K <= N`、唯一窗口位置、非负容量和合法失败索引；它们不是生产 API。原始位置唯一，故元组的第三项请求引用不会成为次级排序键。没有使用类型标签。

默认 K 为 8、24、32、128、512、1024；A 取 1、2、4、8、K/2、K，裁剪和去重。四种分数分布为随机、升序、降序及大量同分。额外固定 K=24、128 和 A=1、K，对 N=4096、65536 做窗口尾部对照。默认每案例每方法预热一次，正式测量三批、每批三次，各方法以轮转顺序运行；同一批独立 deque 在计时前生成。GC 在所有测量与预热时统一关闭，之后恢复原状态。无第三方依赖。

输出 JSON 保存所有每批平均每次耗时、运行顺序和每案例汇总；median、min、max 以及 nearest-rank P95/P99 的样本单位都是**批次平均每次耗时**，不是独立调用延迟的真实 P95/P99。三批仅是快速演示，尾部分位数证据很弱；可增加 repeats 和 batch。数据生成、队列初始准备、打印与文件写入均在计时外。结果记录 Python、执行程序、平台、CPU、Git HEAD、已跟踪文件脏状态、参数、种子、时钟和 GC 策略。建议在干净提交上运行；不同主机、运行时及 CPU 负载都会影响结果。

从仓库根目录运行（`python` 可替换为实际 Python 可执行路径）：

```bash
python -B tools/r1_selection_microbench/test_selection.py -v
python -B tools/r1_selection_microbench/bench.py --k 8,24,32,128,512,1024 --tail-k 24,128 --tail-n 4096,65536 --seed 20261027 --warmup 1 --repeats 3 --batch 3 --output /tmp/r1_selection_microbench.json
```

理论复杂度不等于实测更快；结果不包含真实预测、KV 分配、完整 `schedule()`、E2EL 或服务总开销，Codex 环境数据不能替代用户服务器复测。原有 8/128/32 只是此前影子实验配置，预测频率、扫描范围、候选数仍待设计。真实 waiting 重排前须明确窗口外公平性、特殊请求处理、skipped 回填、预测失效和跳过预测时的行为。本实验不选择最终调度公式，也不证明收益。
